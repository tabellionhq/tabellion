# ADR-0030: Plugin HTTP binding

- Status: Proposed
- Date: 2026-10-29
- Drafted by: agent (Claude Code, claude-opus-5-5)

## Context

### Problem

The specification says what a plugin receives and returns (Section 7), not how it travels. Without a binding, a plugin built by someone else cannot be plugged into a server, and our `model` plugin has no interface to build against.

Already decided: plugins are services reached by URL (ADR-0028); a plugin declares its kinds and options, and is called only for those (specification 4.10, 7.1); errors are problem details [RFC 9457] (7.1); TLS once a plugin is outside the host or private network (Security Considerations); a plugin keeps nothing it receives once it has answered (4.10).

Not decided: addresses and methods, how a plugin describes itself, slow calls, who may call a plugin, how contracts are versioned and published.

### Factors

- Stateless plugins (4.10): a plugin that holds a result until the server fetches it keeps personal data after the work is done.
- Slow work: term matching on a long text, by a language model, may take tens of seconds or more. How slow is not known until the AI question is settled (design backlog: AI roles and search).
- The server already runs slow work as a task with stages, stoppable by the owner (4.7): the call to a plugin happens inside a task, not inside the owner's request.
- Deployments: the demo compose puts the core and plugins on one private network; a provider may run a plugin elsewhere, over the internet.
- Hypermedia API, JSON-LD with actions (ADR-0015); contract first, code generated by `oapi-codegen` (ADR-0023). Plugins are written in other languages (TypeScript, Rust), which also generate from OpenAPI.
- Reverse proxies often serve a service under a path prefix: a plugin's base URL may be `https://example.org/plugins/model/`.

## Options

### 1. Self-description

| Option | Issues | Impacts |
|---|---|---|
| A. `GET` on the base URL returns the description, with an action per kind: method, target, media types | Same pattern as the core's entry point (ADR-0015) | Works under a path prefix; one URL to configure |
| B. `GET /.well-known/tabellion-plugin` | Well-known URIs sit at the host root (RFC 8615): breaks under a path prefix; a public name is registered with IANA | Conventional for discovery across hosts |

### 2. Slow calls

| Option | Issues | Impacts |
|---|---|---|
| C. Synchronous: `POST`, the plugin answers when done; the server sets a timeout; closing the connection stops the work | A long call needs timeouts raised along the way (proxies) | Nothing kept after the answer (4.10); stop is free; simplest for plugin authors |
| D. Asynchronous: `202 Accepted` with a job URL; the server polls, then fetches the result | The plugin holds the result until fetched: state and personal data kept after the work, against 4.10 | Survives proxy timeouts; progress per poll |
| E. Synchronous with a progress stream: the answer is a stream of progress events, then the result (e.g. NDJSON) | Streaming support needed in clients and proxies | Progress shown in the task's stages; nothing kept; stop by closing |

### 3. Who may call a plugin

| Option | Issues | Impacts |
|---|---|---|
| F. Nothing on a private network; a bearer token, set on both sides, otherwise | Two settings to keep in step; a token to rotate | Zero setup for the demo compose; a provider can refuse unknown servers |
| G. Mutual TLS | Certificates to issue and renew on both sides | Strongest; heavy for self-hosting (APR-0002) |
| H. Nothing | Anyone who reaches a plugin uses it, e.g. a paid provider's model | Only for localhost |

### 4. Contracts and versions

| Option | Issues | Impacts |
|---|---|---|
| I. One OpenAPI 3.1 file per kind, in `api/plugins/`, published with the core's contract; a kind name carries its major version (`term-matching/1`); the description names the specification revision | A file per kind to keep in step with Section 7 | Code generated on both sides; a breaking change is a new kind name, so old and new plugins coexist |
| J. Version in the path (`/v1/term-matching`) | Couples the address to the version | Familiar; the description already gives addresses, so it adds nothing |

## Recommendation

- A: the description at the base URL, with an action per kind.
- C now, E when the AI question shows calls long enough to need progress. D is refused by the stateless rule.
- F: nothing on a private network, a bearer token otherwise, always with TLS outside the host or private network.
- I: one OpenAPI file per kind in `api/plugins/`, kind names with a major version.

Settle the rest after the AI question: timeouts, body size limits, whether E is needed from the start.
