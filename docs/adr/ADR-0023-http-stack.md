# ADR-0023: HTTP stack

- Status: Proposed
- Date: 2026-10-22
- Drafted by: agent (Claude Code, claude-opus-5-5); preference for Gin stated by owner

## Context

The server is in Go (ADR-0014). The HTTP API is defined by an OpenAPI 3.1 contract, `api/openapi.yaml` (ADR-0015). The contract is the source: server code is generated from it, requests are validated against it.

Constraints:

- Easy maintenance; code that people and agents already know well.
- Add no dependency the standard library covers.
- `CGO_ENABLED=0` on all targets (ADR-0020).

Since Go 1.22, the standard library router matches methods and path parameters (`GET /practices/{id}`).

## Options

| Option | Licences | OpenAPI 3.1 | Issues |
|---|---|---|---|
| A. Gin, server generated by `oapi-codegen` (gin target), validation by `kin-openapi` | MIT, Apache-2.0 | `oapi-codegen` v2.8: "initial" 3.1 support; `kin-openapi`: supported | Gin brings many indirect dependencies (e.g. `quic-go`, `mongo-driver`); widely known, many middlewares |
| B. Standard library, server generated by `oapi-codegen` (std-http target), validation by `kin-openapi` | Apache-2.0, MIT | Same as A | Fewer dependencies; middlewares written by hand or taken one by one |
| C. `ogen`, its own generated `net/http` server | Apache-2.0 | Not verified | Fewer users; no Gin |
| D. Huma, code first, contract generated from Go code | MIT | Produces 3.1 | The YAML contract is no longer the source |

Not verified for A and B: `$ref` with sibling keywords and our `x-actions` extension in `oapi-codegen`. Indirect dependency licences: to check with `go-licenses` in CI.

## Recommendation

B, the standard library with `oapi-codegen`: same generated code and validation as A, fewer dependencies. A if Gin middlewares are wanted.

First step for A or B: generate the server from `api/openapi.yaml`, in Docker, and check what the generator does not handle.
